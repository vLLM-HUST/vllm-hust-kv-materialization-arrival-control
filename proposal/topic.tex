\begin{frame}{研究问题}
  \begin{itemize}
    \item 现代LLM服务系统越来越容易暴露可复用的前缀或KV状态。
    \item 但\alert{可复用状态的存在}并不自动意味着\alert{端到端延迟下降}。
    \item 真正把这些状态“兑现”为收益，可能需要跨worker传输、主机到设备搬运、部分重构以及额外的元数据管理。
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{核心系统问题}
    当多个可复用 session 在固定 KV block 预算下重叠时，
    \texttt{always\_full\_reuse} 是否会逐出更高价值状态，或阻塞无缓存关键请求？
  \end{block}
\end{frame}

\begin{frame}{研究范围与论文主张}
  \begin{itemize}
    \item M2 已证明旧 request-local 三动作控制器输给最强固定策略，禁止继续调阈值或挑 workload。
    \item 新问题只研究\alert{有限缓存占用的跨请求外部性}，不扩展成通用调度器或状态管理。
    \item connector 分支必须先有非零传输 bytes、queue wait、completion identity 和双 endpoint receipt。
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{论文主张}
    负结果只关闭旧机制；新的 admission 机制必须先由无 treatment 的固定策略 crossover 证明有必要。
  \end{block}
\end{frame}

\begin{frame}{新主线必须先过 D0}
  \begin{itemize}
    \item 固定臂：\texttt{always\_full\_reuse}、\texttt{always\_recompute}、旧控制器、固定并发门、固定 KV block 门、原生 cache policy。
    \item oracle：future-aware offline oracle 只给上界，不是 online treatment。
    \item Go 门：至少两个预注册高压 cell 出现固定策略 winner switch，且全复用 p95 TTFT 至少差 10\% 或 SLO goodput 至少低 5\%。
    \item 正确性：request/output、block/generation/owner/refcount、action receipt 与 cleanup 必须 100\% 一致。
  \end{itemize}

  \begin{block}{停止条件}
    无 crossover、静态控制已匹配 oracle、原生 receipt 无法归因、或任何 stale/ABA/orphan/cleanup 错误，都在实现新 treatment 前停止。
  \end{block}
\end{frame}

\begin{frame}{三动作决策面（旧机制，已关闭）}
  \begin{itemize}
    \item \texttt{full\_reuse}：直接兑现已有前缀/KV状态。
    \item \texttt{partial\_reuse}：只复用高价值前缀段，剩余尾部重新计算。
    \item \texttt{recompute}：放弃兑现已有状态，直接重算。
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{当前offline语义}
    \texttt{partial\_reuse} 已从“固定半截复用”改成\alert{切点优化问题}：
    \[
      r^* = \arg\min_r\; \bigl(\mathrm{materialization\_cost}(r) + \mathrm{recompute\_cost}(\mathrm{tail}(r))\bigr)
    \]
  \end{block}

  \begin{itemize}
    \item 这样 policy、baseline 和 oracle 共享同一套三动作含义。
  \end{itemize}
\end{frame}

\begin{frame}{什么时候别直接全复用}
  \begin{block}{核心判断}
    不是“能复用就全复用”，而是：\alert{后半段拿回来，到底还值不值。}
  \end{block}

  \begin{columns}[T]
    \begin{column}{0.49\textwidth}
      \scriptsize
      \begin{block}{\texttt{partial\_reuse} 更优}
        \begin{itemize}
          \item 前面很多内容是固定的，后面经常变
          \item 前面复用收益大，后面复用收益小
          \item 典型：固定提示词/工具框架 + 最近一轮对话或检索结果
        \end{itemize}
      \end{block}
      直觉上：\alert{只复用前面稳定的部分。}
    \end{column}
    \begin{column}{0.49\textwidth}
      \scriptsize
      \begin{block}{\texttt{recompute} 更优}
        \begin{itemize}
          \item 能复用的内容太少
          \item 这段内容变化太大，不值得搬回来
          \item 拿回来再接起来，比自己重算还贵
        \end{itemize}
      \end{block}
      直觉上：\alert{既然不划算，那就别复用。}
    \end{column}
  \end{columns}

  \vspace{0.3em}
  \begin{block}{学生版记忆法}
    大部分都稳定 $\rightarrow$ \texttt{full\_reuse}；前面稳定后面易变 $\rightarrow$ \texttt{partial\_reuse}；可复用太少或太不稳定 $\rightarrow$ \texttt{recompute}。
  \end{block}
\end{frame}

\begin{frame}{证据边界必须分开}
  \begin{columns}[T]
    \begin{column}{0.49\textwidth}
      \begin{block}{Offline决策研究}
        \begin{itemize}
          \item 解释三动作在不同工作负载下何时更优
          \item 关注决策结构、敏感性和headroom
          \item oracle 只作为上界，不作为可部署结果
        \end{itemize}
      \end{block}
    \end{column}
    \begin{column}{0.49\textwidth}
      \begin{block}{Online运行时验证}
        \begin{itemize}
          \item 检查当前插件与runtime seam到底能兑现多少
          \item 允许出现负结果或边界结果
          \item 不能把offline优势直接写成live收益
        \end{itemize}
      \end{block}
    \end{column}
  \end{columns}

  \vspace{0.5em}
  \alert{历史边界：offline只给决策上界；M2已证明旧控制器未胜过最强固定策略。}
\end{frame}

\begin{frame}{当前系统已经做到什么（历史证据）}
  \begin{itemize}
    \item 已完成三动作 offline policy 与 evaluator。
    \item 已接入 \texttt{llm-serving-workloads} 作为共享 workload source of truth。
    \item 已有插件侧 live control：从请求头估计信号、做决策、设置 cache salt、传递 cut point。
    \item 已在 \texttt{carrier/vllm-hust} 中推进到第二版 segmented seam：\texttt{target\_reuse\_tokens} 不仅截断 prefix-cache lookup，也会截断 shared-cache commit，并在 reuse boundary 之后重置 tail hash chain。
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{当前truthfulness boundary}
    现在的online \texttt{partial\_reuse} 已能以\alert{block对齐后的segmented prefix-cache动作}执行：
    共享前缀与重算尾部已经在 carrier seam 上进入不同哈希命名空间，
    但还不是 connector-backed、exact token-level 的完整 segmented materialization path。
  \end{block}
\end{frame}

\begin{frame}{旧 M2 真实实验设置}
  \begin{itemize}
    \item 模型：Qwen2.5-7B-Instruct
    \item 运行环境：carrier内本地 vLLM runtime，开启 prefix caching
    \item Ascend live路径实际 block size 会固定到 \textbf{128}，因此 partial cut point 必须先做 block 对齐
    \item 本轮对比对象：
    \begin{itemize}
      \item \textbf{旧 baseline}：旧 seam，\texttt{floor=256}，\texttt{confidence\_penalty=4.0}
      \item \textbf{旧 tuned}：旧 seam，\texttt{floor=128}，\texttt{confidence\_penalty=8.0}
      \item \textbf{新 baseline}：新 segmented seam，\texttt{floor=256}，\texttt{confidence\_penalty=4.0}
      \item \textbf{新 tuned}：新 segmented seam，\texttt{floor=128}，\texttt{confidence\_penalty=8.0}
    \end{itemize}
    \item 代表场景：
    \begin{itemize}
      \item \texttt{shared\_scenario\_multi\_turn\_knowledge\_service}
      \item \texttt{shared\_tool\_scaffold\_agent}
    \end{itemize}
    \item 新增 runtime-boundary live补充验证：
    \begin{itemize}
      \item 成功跑通：\texttt{shared\_prefix\_multi\_tenant\_assistant}、\texttt{session\_continuation\_with\_maintenance}
      \item 更正后的第三个 case：\texttt{dynamic\_rag\_corpus\_update} 在使用真实 Qwen tokenizer 生成 workload 后可稳定跑通
    \end{itemize}
  \end{itemize}
\end{frame}

\begin{frame}{当前修复与边界解释}
  \begin{itemize}
    \item 已修复的一点：本地 runtime control 不再错误占用 \texttt{kv\_transfer\_params}，而是改到独立的 materialization-control payload。
    \item 已新增的一点：live \texttt{partial\_reuse} 会先按 block size 对齐，再在 \texttt{partial/full/recompute} 间重排可实现动作。
    \item 已推进的一点：carrier seam 现在不只截断 lookup 和 commit，还会在 reuse boundary 之后用 request-scoped salt 重置 tail hash chain。
    \item 这让当前 online 结果的语义更诚实：
    \begin{itemize}
      \item 它确实在测试一个 block-aligned segmented prefix-cache runtime seam；
      \item 但它还没有进入 connector-backed KV transfer/materialization 路径。
    \end{itemize}
    \item 四格矩阵仅为旧机制历史诊断；它不能推翻 matched M2 的负结果。
  \end{itemize}

  \vspace{0.5em}
  \begin{block}{更准确的结论}
    现阶段可支持的结论是：\alert{旧 controller 与阈值路线已关闭}；有限缓存外部性仍未观察到。
  \end{block}
\end{frame}

\begin{frame}{下一步工作}
  \begin{itemize}
    \item 学生 owner 只执行预注册、无新 treatment 的 D0 fixed-policy crossover。
    \item 强基线必须包含 \texttt{always\_full\_reuse}、\texttt{always\_recompute}、冻结旧 controller、固定容量/并发门和原生 cache policy。
    \item D0 保存原生 block/victim/residency/wait/action/completion/cleanup receipt；future-aware oracle 仅作离线上界。
    \item 若没有固定策略 winner switch，或无法由 receipt 解释，立即停止有限缓存新假设；不得回到阈值、seam 或 connector 调优。
  \end{itemize}

  \vspace{0.6em}
  \begin{block}{答辩时最重要的一句话}
    当前唯一问题是：\alert{full reuse 在有限缓存下是否对并发请求产生可测外部性}；答案尚未知。
  \end{block}
\end{frame}

\begin{frame}{总结}
  \begin{enumerate}
    \item M2 已关闭旧 request-local 三动作 controller、旧阈值和 seam continuation。
    \item 新主线是尚未观察到的有限缓存跨请求外部性，不是对旧机制重新调参。
    \item D0 不含 adaptive treatment；只有原生 receipt 支持的 fixed-policy crossover 才能 admit M1。
    \item 实施、环境、实验与结果生成仍由学生 owner 完成；失败门触发即停止。
  \end{enumerate}
\end{frame}
